# Container create and start call-coverage inventory (#68)

Snapshot: `4b88669cd5c337c57ccabfd63bfd506e3637964e`, current #65 draft branch. This is an evidence-bounded inventory of application paths that can create or start containers, including composite restart and Compose. It is not a claim that every possible entry point has been enumerated, nor that #68, #70, or automatic recovery is implemented. No behavior is changed by this document.

## Composition and scope

The app creates one bridge and one `ContainerService`, shares that service with MCP, Compose, project and registry services, and conditionally supplies it to MacLauncher ([app composition](../lib/app/app.dart#L74-L138)). The service's `_operations` map and queue are instance-local, keyed by the supplied container ID; duplicate creates conflict, matching pending writes can join, and later operations wait even if their predecessor fails ([queue](../lib/services/container_service.dart#L716-L785)). IDs are validated and trimmed, but not resolved to a canonical runtime identity before queueing; a name and a different ID alias for the same container can therefore occupy different queues even within one service instance ([start](../lib/services/container_service.dart#L601-L610), [validation](../lib/services/container_service.dart#L890-L903), [queue](../lib/services/container_service.dart#L724-L729)). This is not a runtime-wide fence: an external Docker client or another application/service instance can mutate the same endpoint independently. A management directory is expressly not a security boundary ([ADR 0005](adr/0005-directory-scoped-container-management.md#L5-L9)).

## Observed application paths

| Entry or path | Calls and coverage implications |
| --- | --- |
| `ContainerService.create` | Validates inputs, queues by name, calls `containerCreate`, refreshes, and optionally calls `containerStart` followed by another refresh. Once create returns successfully, a follow-up failure carries `created: true` and the ID; this is not recovery of an unknown create outcome ([create](../lib/services/container_service.dart#L439-L450), [calls and failure](../lib/services/container_service.dart#L524-L599), [wire details](../lib/services/container_service.dart#L1077-L1100)). |
| `ContainerService.start` / `restart` | Start enqueues a bridge start. Restart enqueues stop then start under one resource queue; it is explicitly non-atomic ([lifecycle](../lib/services/container_service.dart#L601-L649)). Docker bridge translates create and start to CLI `container create` and `container start` ([bridge](../lib/bridge/docker_container_bridge.dart#L315-L345)). |
| MCP and desktop | MCP `container_create`, `container_start`, and `container_restart` call the shared service ([MCP](../lib/mcp/tools/container_tools.dart#L155-L208), [restart](../lib/mcp/tools/container_tools.dart#L236-L249)). Container UI create/start/restart, container-detail start, and project-detail start also call it ([container page](../lib/features/containers/containers_page.dart#L123-L140), [actions](../lib/features/containers/containers_page.dart#L146-L180), [container detail](../lib/features/containers/container_detail.dart#L64-L70), [project detail](../lib/features/projects/project_detail.dart#L864-L871)). |
| MacLauncher | For containers with a managed-label prefix, callbacks delegate start and recycle to service start and restart; connection is optional ([callbacks](../lib/launcher/maclauncher_bridge.dart#L93-L107), [composition](../lib/app/app.dart#L123-L138)). |
| Global registry | If absent, registry setup pulls the image then directly invokes CLI `run --detach` (creating and starting), bypassing `ContainerService.create` and its queue; an existing stopped registry instead uses `ContainerService.start` ([registry flow](../lib/services/registry_service.dart#L179-L214), [direct run](../lib/services/registry_service.dart#L245-L267)). `BridgeProjectCli.run` delegates to bridge `cliRun` ([adapter](../lib/bridge/project_cli_adapter.dart#L9-L20)). |
| Project test runner | Both explicit `testProject` and optional post-build testing use `_runTestProcess`, which directly starts CLI `run --rm` with project/test labels; it bypasses the container service queue ([post-build](../lib/services/project_service.dart#L645-L655), [testProject](../lib/services/project_service.dart#L706-L726), [runner](../lib/services/project_service.dart#L1175-L1195), [adapter](../lib/bridge/project_cli_adapter.dart#L14-L20)). |
| Compose | UI and MCP can call `ComposeService.up`; it builds `compose ... up --detach`, with optional dry-run and force-recreate, and invokes bridge `composeRun`, not per-container service create/start ([UI](../lib/features/compose/compose_page.dart#L62), [MCP](../lib/mcp/tools/compose_tools.dart#L59-L69), [service](../lib/services/compose_service.dart#L165-L198), [dispatch](../lib/services/compose_service.dart#L225-L228), [Docker bridge](../lib/bridge/docker_container_bridge.dart#L546-L554)). Compose controls its resulting resources. |

These direct paths are present in the #65 draft and bypass the service queue; the existence of identity primitives does not mean they cover these calls. Global container operations remain as currently implemented, including the shared service and registry paths above; this inventory proposes no change to global calls.

## Identity primitive: reachability qualification

`ContainerRuntimeIdentityService` defines separate complete-output CLI create and identity-checked start primitives ([create](../lib/services/container_runtime_identity.dart#L16-L78), [start](../lib/services/container_runtime_identity.dart#L156-L179)). Its own comments say it does not persist intent or register ownership; labels are consistency markers, not authorization ([identity](../lib/services/container_runtime_identity.dart#L5-L12), [create](../lib/services/container_runtime_identity.dart#L28-L30)). A search of production `lib/` for the class found only its definition and internal references, and the inspected application composition does not construct it. Thus no application create/start route to this primitive was established in this snapshot; its existence must not be counted as coverage of the routes above. The query itself cannot rule out concurrent runtime mutation or an in-flight create ([query](../lib/services/container_runtime_identity.dart#L81-L84)).

## Existing test evidence (not runtime validation)

- Fake-bridge service tests exercise create argument forwarding and optimistic state, created-resource details after start failure, and duplicate-create rejection ([create tests](../test/services/container_service_test.dart#L304-L418)); they also check same-start joining and restart stop/start ordering ([queue tests](../test/services/container_service_test.dart#L574-L613)).
- Registry service tests use a fake container bridge ([setup](../test/services/registry_service_test.dart#L63-L72)); Compose tests use a fake bridge and check `up` argument passthrough ([setup](../test/services/compose_service_test.dart#L11-L22), [passthrough](../test/services/compose_service_test.dart#L120-L146)). Project service tests check `run --rm` arguments ([project test](../test/services/project_service_test.dart#L493-L537)).
- Identity-specific tests exercise exact identity and full-ID start verification and failure cases ([identity tests](../test/services/container_runtime_identity_test.dart#L333-L452)); these are tests of the primitive, not proof of application reachability or external-client fencing.

These examples describe existing tests, not a test run or proof of real Docker behavior, crash recovery, terminality, or cross-client exclusion.
