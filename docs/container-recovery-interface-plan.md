# 容器恢复：调用迁移和运行时身份计划

状态：**待验证的实施计划，不是已实现能力**。本计划补充[请求终止确认提案](container-request-completion-design.md)，不解除 [PR #65](https://github.com/Ghost233/GhostContainerManager/pull/65) 的草稿限制，也不证明 [#61](https://github.com/Ghost233/GhostContainerManager/issues/61) 已完成。

## 当前接缝和限制

现有全局容器创建、启动和重启由共享管理入口调用运行时桥接；MCP、界面和其他集成复用这些入口。目录创建恢复所需的登记和身份核对尚未接入完整调用链。#65 的保留原语仍是局部探索：旧登记入口可绕过其资源冲突检查，不能据此声称保留对所有调用生效。

本地保留只能协调遵守同一规则的调用方，不能阻止外部 Docker 客户端、直接访问引擎的调用或已在途请求。没有经验证的跨崩溃请求终止证据时，未知必须持续待核对；一次查询、CLI 退出或超时都不是终止证明。保守保留可能无限期阻止同一资源的新操作，不能承诺自动解锁或自动恢复。

## 建议的实施顺序

1. **确定调用覆盖范围。** 盘点共享入口及其创建、启动、重启等组合路径，标明哪些可能与目录操作竞争；全局调用的既有外部契约应保持兼容。梳理直接桥接或其他绕过路径及外部客户端限制，不能把局部互斥描述为全局 fencing。
2. **统一登记规则。** 在同一持久化和跨进程协调接缝中，使旧意图写入与新资源保留双向检查；冲突和不可验证状态失败关闭。先定义旧记录解释、未完成操作枚举和修复策略，再迁移调用方，避免新旧入口并存时互相绕过。保留原语、操作 ID、目录归属唯一性和运行时对象身份各有不同职责，不能相互替代。#65 中未经验证的端点、摘要输入及重复 JSON 键处理也需解决后才能复用。
3. **验证运行时身份。** 在实际支持的 Docker 兼容端点上寻找能稳定、可信区分引擎及其重建的身份来源，并明确取得、持久保存、重启复验与不匹配处理。context 名称、socket 路径或调用方任意字符串不单独构成证明；身份不可证明或发生变化时，不在新端点继续旧操作。不得将凭据或敏感请求内容存入登记。
4. **接入执行与恢复。** 只有在实际适配器能提供对应操作和端点的可验证终止证据时，才进入身份核对及后续登记；其他情况保留未知。分别处理创建和启动，明确直接完整响应、持久化前崩溃、重启恢复、零／多匹配和写入失败。不得自动重复、接管或删除未知操作的资源。
5. **分阶段验证。** 先测试新旧入口交错、并发和进程重启下的互斥及持久记录损坏，再从共享入口测试调用兼容和失败路径；最终在限定资源范围的真实运行时验证适配器的实际保证。模拟证明不了真实引擎侧终止，也不等于断电持久性。

## 必须先解决的问题

- 受支持的运行时是否暴露足以验证的持久引擎身份？如不能，需明确哪些恢复场景必须永久保持未知，而非用可变连接地址冒充身份。
- 如何在不改变全局调用方既有可见行为的前提下协调所有会竞争的应用内入口？若无法兼容，须明确受影响调用方与迁移契约，不能以一个局部模块补丁宣称完成。
- 哪个可用执行方能提供跨应用和执行方崩溃的终止与可见性保证？尚无证据时保留保守退路，不把包装进程或本地日志当作权威终态。
- 如何处置历史未完成记录、不可读或重复键记录，以及无法验证身份的遗留保留？处理不得静默释放或推断所有权。

上述问题解决前，这只是可审查的路线，不授权绕过未知状态或声称自动恢复可用。实际设计和验证结果应更新相关工单；任何改变调用方契约或模块职责的实施都需要作为协调工作单独安排。
